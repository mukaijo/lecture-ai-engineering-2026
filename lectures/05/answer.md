# 第5回 解答

## 演習

- 回答モデル（実行時の`[model]`）：gemini-3.5-flash-lite
- 比較した質問："第2回の説明では、LoRAは何を固定し何を学習しますか？ QLoRAは何を加えますか？"
- 対象資料（全文投入と他の方式で範囲が違う点も記録）：
    - データソースは rag_data に格納された講義資料のJSONファイル。
    - 全文投入は lectures.json に含まれる全資料を対象とする。
    - ベクトル検索は index.sqlite3 に格納されたページ単位のベクトル索引を使用する。
    - Treeは tree.json の目次構造、Graphは graph.json の関連情報を利用し、lectures.json からページ本文を取得する。
    - 全文投入以外の方式は、設定された対象資料（第1〜3回の本講義資料）に検索範囲を限定している。

|---|---|---|---|---|---|---|

- 検索だけを実行して見つかったページと、その本文で確認できたこと：
    - 検索結果の上位5件は、第2回のPDF p.52、p.51、p.60、p.47、p.61だった。
    - 最も関連性の高いp.52が1位となり、LoRAは元の重みを固定して小さな行列A・Bを学習すること、QLoRAはさらに元の重みを4bitに量子化することを確認できた。
一方、p.60やp.61など、質問への直接的な回答ではないページも検索された。
- `--trace`で見えたツール呼び出し（ツール名・引数・回数、Treeでたどった目次など）：
    - 全文投入：ツール呼び出しなし。モデル応答1回。
    - ベクトル検索：search_materials({'query': 'LoRA QLoRA 固定 学習'}) を1回呼び出し。モデル応答2回。
    - Tree：browse_tree を4回呼び出し。以下の順番で目次をたどった。
        講座資料全体（{}）
        第2回「基盤モデルの仕組み」（{'node_id': 'lec02-main'}）
        「選んだモデルを、いつ・どう直すか」（{'node_id': 'lec02-main-s045'}）
        PDF p.52（{'node_id': 'lec02-main-p052'}）
    - Graph：search_graph({'query': 'LoRA QLoRA 固定 学習'}) を1回呼び出し。モデル応答2回。
- 取得した情報が足りなかった例、取得できたのに回答へ使えなかった例：
    - Graphでは正しい回答が得られたものの、Treeと比較すると補足情報が少なかった。ただし、今回の質問に回答するための情報は十分に取得できていた。
    - 全文投入ではPDF p.51、p.52を正しく特定できたが、資料を確認するよう促すヒント中心の回答となった。これは、プログラムの指示に「宿題の答えそのものは書かず、考え方のヒントで導く」と記載されていることが影響したためと考えられる。
    - このことから、必要な情報をモデルに渡すことと、その情報を適切に利用して回答を生成することは別の課題だと感じた。
- 今回の用途に採用したい方式と、その理由・比較条件の限界：
    - 講義資料に基づいて質問に回答する用途では、ベクトル検索を採用したい。
    - 4方式とも概ね正しい回答を生成したが、ベクトル検索は3.07秒、入力3,027 tokens、生成API推定コスト$0.001363であり、正確性と処理負担のバランスが良かった。
    - 全文投入は2.33秒と最速だったが、入力117,025 tokensと多く、生成API推定コストも$0.004834だった。
    - Treeは6.22秒、モデル応答5回と負担が大きかった一方、目次をたどって適切なページを特定し、詳細な回答を生成できた。
    - Graphも正しい回答を生成できたが、今回の質問ではベクトル検索に対する明確な優位性は確認できなかった。
- 気づき・疑問：
    - 全文投入は大量の情報を渡すため正確な回答が得られると思っていたが、今回の実験では必ずしも期待した回答にならなかった。ただし、回答にはプログラムの指示も影響するため、情報量の多さだけが原因とは判断できない。
    - Treeは目次を段階的にたどるため、人間が資料を調べる方法に近いと感じた。一方、LLMの呼び出し回数が増えるため、処理時間やコストが大きくなることも確認できた。


## 宿題

- 取り組んだレベル：基礎
- やったこと（変更したファイル・設定・処理、または設計した取得方法）：
    - app/agent.py の INSTRUCTIONS にある指示文を変更した。
    - 変更前：「根拠ごとに『第N回・PDF p.N』を付ける。」
    - 変更後：「回答には、根拠となる資料の内容を簡潔に説明し、根拠ごとに『第N回・PDF p.N』を付ける。」
    - 引用ページだけでなく、根拠となる内容を明確に説明させることを意図した。
- 比較した質問と、固定した条件（モデル・対象資料など）："第2回の説明では、LoRAは何を固定し何を学習しますか？ QLoRAは何を加えますか？"
- 結果（変更前後の回答・根拠、`--trace`の出力、時間・トークン数・生成API推定費用など）：

| 項目 | 変更前 | 変更後 |
|---|---|---|
| 回答時間 | 3.07 秒 | 3.32 秒 |
| 入力トークン | 3,027 | 3,061 |
| 出力トークン | 182 | 244 |
| モデル応答回数 | 2回 | 2回 |
| ツール呼び出し回数 | 1回 | 1回 |
| 生成API推定コスト | $0.001363 USD | $0.001528 USD |

- 改善した例と、残る失敗・制約：
    - 変更前もLoRAとQLoRAの違いについて正しく回答し、第2回のPDF p.51、p.52を引用できていた。
    - 変更後は、LoRAが固定する元の重みと、学習する小さな行列A・Bを分けて説明するようになった。また、QLoRAについても、4bit圧縮によるメモリ削減効果を補足していた。
    - ツール呼び出しは変更前後とも search_materials を1回実行していたが、検索語は変更されていた。
    - 出力トークン数は182から244に増加し、生成API推定コストも増加した。
- 気づき・疑問：
    - 指示文の変更後は、回答がより具体的になり、根拠となる資料の内容も分かりやすく説明されるようになった。
    - 一方、変更前から正しい回答と引用ページは得られており、今回の変更による正確性の向上までは確認できなかった。
    - また、指示文の変更によって回答の情報量が増えると、出力トークン数やコストも増えることが分かった。
    - ただし、検索語も変わっており、実行回数も各1回のため、これらの変化が指示文の変更だけによるものとは断定できない。
    - 今回の実験から、検索結果を取得するだけでなく、その情報をどのように回答に反映させるかも重要だと感じた。
